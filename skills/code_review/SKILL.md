# 代码审查流程（skill: code_review）

按以下四步执行，每步产出明确结论后再进入下一步。审查意见按
[blocking / should-fix / nit] 三级标注，blocking 指会引发正确性/安全问题。

## 第一步：结构与契约

1. 先读目录结构，识别模块分层（入口 / 业务 / 数据 / 工具层），确认改动
   是否跨越了分层边界（如业务层直接拼 SQL）。
2. 找出对外契约（API 入参/返回、事件字段、schema 定义），确认本次改动
   没有破坏既有字段语义——字段名不许随意增改，新增必须可选。
3. 检查配置与密钥：密钥绝不出现在代码/配置文件/日志中。

## 第二步：逻辑与边界

1. 逐函数检查输入校验：类型、空值、越界、超长输入是否都有归一化处理。
2. 异常路径：失败必须归一化为结构化错误（错误码 + 可执行建议），不允许
   裸异常逃逸到调用方；重试只对瞬时失败，永久失败立即返回。
3. 资源生命周期：连接/子进程/文件句柄必须显式关闭；异步任务要有取消
   传播路径，取消时清理已占用资源。
4. 并发正确性：共享状态是否有锁保护；并行任务失败是否相互隔离
   （一个失败不应拖垮同批其他任务）。

## 第三步：正确性不变量（对 agent/工具类项目尤其重要）

1. 配对完整性：请求-响应、tool_use-tool_result 必须一一配对，中断路径
   也要合成占位结果，绝不允许孤儿请求。
2. append-only：历史/日志只追加不修改；需要"反悔"时用快照回滚重来。
3. 幂等与重试：同一操作重复执行不产生重复副作用。

## 第四步：测试与输出

1. 每个新行为至少一条正向 + 一条边界/失败用例；异步逻辑覆盖超时与取消。
2. 输出格式：按文件分组列意见，每条含 位置 / 等级 / 问题 / 建议改法，
   最后给一段总体结论（可合并 or 需返工）。
